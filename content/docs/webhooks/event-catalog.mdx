---
title: Event catalog
description: Every webhook event type, when it fires, and a full example payload for each.
---

Every event uses the same [envelope](/docs/webhooks#the-event-envelope). `data.referral` is the [referral object](/docs/api-reference/referrals#the-referral-object) **without** the `patient` block. Patient personal data is never sent in webhooks.

The examples below follow one live referral, `RHB-4829173655`, from creation to completion, followed by three other outcomes. Its `data.sequence` goes up by 1 with each event. IDs and timestamps are illustrative.

| Type | When it fires | `data.previous_status` |
| :--- | :--- | :--- |
| [`referral.created`](#referral-created) | A referral is created (API, referral-link lead, or portal) | `null` |
| [`referral.contacted`](#referral-contacted) | Patient reached / intake started (incl. patient messaged Joy with the tracking code) | Usually `received` |
| [`referral.provider_matched`](#referral-provider-matched) | A physiotherapist was assigned | The current status (matching doesn't change it) |
| [`referral.booked`](#referral-booked) | First appointment confirmed (payment verified or care covered) | Usually `contacted` |
| [`referral.in_treatment`](#referral-in-treatment) | Treatment under way | Usually `booked` |
| [`referral.completed`](#referral-completed) | Care episode completed | Usually `in_treatment` |
| [`referral.not_suitable`](#referral-not-suitable) | Not appropriate for Rehabify services | The status before the change |
| [`referral.cancelled`](#referral-cancelled) | Cancelled / refunded | The status before the change |
| [`referral.closed`](#referral-closed) | Closed | The status before the change |
| [`ping`](#ping) | Test event from the portal or `POST /sandbox/trigger-webhook` | Not present |

## `referral.created` [#referral-created]

Fires as soon as a referral is created, whether through the API, a [referral-link](/docs/guides/no-code-referral-links) lead or the Partner Portal. `previous_status` is `null`.

  "created_at": "2026-10-13T09:30:00.000Z",
  "environment": "live",
  "data": {
    "previous_status": null,
    "sequence": 1,
    "referral": {
      "object": "referral",
      "id": "jd7f3k2m9x1q8w4e5r6t7y8u9i0o1p2a",
      "tracking_code": "RHB-4829173655",
      "partner_reference": "HMO-REF-2026-0091",
      "environment": "live",
      "status": "received",
      "clinical": {
        "condition": "Lower back pain",
        "priority": "standard",
        "recommended_sessions": 6,
        "referring_clinician": "Dr. Okafor"
      },
      "care": { "preferred_mode": "patient_choice", "preferred_contact_channel": "whatsapp" },

## `referral.provider_matched` [#referral-provider-matched]

Matching doesn't change the status, so `previous_status` equals the referral's current `status`. `referral.provider` now holds the physiotherapist's `name` and `license_number`. ## `ping` [#ping]

A test event sent from the portal or with [`POST /sandbox/trigger-webhook`](/docs/sandbox/testing#trigger-a-test-webhook). `data` contains a `message` and a `referral`. ## Test events for other types

When you trigger any type other than `ping` from the portal or with `POST /sandbox/trigger-webhook`, the event has the normal envelope and is signed like a real one, but its `data` is marked as a test:

| Field | Value in a test event |
| :--- | :--- |
| `data.previous_status` | `null` |
| `data.sequence` | `0` |
| `data.test` | `true` |
| `data.referral` | The sandbox referral you named in `referral_id`, or the sample referral shown above |

Real events never include `data.test`. Test events don't change the referral, so you can ignore them in your ordering logic.
